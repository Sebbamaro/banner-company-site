# Российский виртуальный хостинг

1. Выберите российский сервер с PHP 8.2+, PDO MySQL, mbstring, curl, OpenSSL, MySQL 8+ или MariaDB 10.6+ (SKIP LOCKED), cron, SSH/SFTP. Данные и резервные копии заявок — в РФ. Уточните договоры и получателей данных. Обязательных платных SaaS нет.
2. Выгрузите проект в отдельный каталог, например `/home/user/banner`. Укажите **document root `/home/user/banner/public`**, не корень проекта. Если тариф не позволяет менять root, запросите настройку у хостера или выберите подходящий тариф. PHP built-in server только для разработки.
3. Создайте базу и отдельного пользователя с нужными SELECT/INSERT/UPDATE/DELETE; миграции выполняйте отдельной учётной записью с CREATE. `composer install --no-dev --prefer-dist --no-interaction --optimize-autoloader`. Скопируйте `.env.example` в `.env`, права 600, не коммитить. vendor, config, bin, storage и .env находятся вне web root.
4. Заполните config/company.json и юридические документы, пересоберите страницы на локальной машине, загрузите результат. Пока домен пуст, canonical отсутствует, robots запрещает индексацию и sitemap пуст. Укажите `https://реальный-домен.ru` и пересоберите. Не публикуйте placeholders. Не используйте PHP-обработчик с незаполненным оператором.
5. APP_MODE=production, APP_ENV=production; DB_DSN, DB_USER, DB_PASSWORD; APP_ORIGIN точный HTTPS origin без завершающего слеша; RATE_SALT случайный секрет 32+ символа; RETENTION_DAYS согласованный срок. `php bin/migrate.php` создаёт таблицы без удаления данных. Перед миграциями резервная копия; последующие изменения схемы требуют отдельного контроля.
6. SMTP_HOST/PORT/USER/PASSWORD/FROM/MAIL_TO; SMTP_SECURITY=tls для STARTTLS (587) либо ssl (465). FROM — подтверждённый адрес компании, настройте SPF/DKIM/DMARC у почтового провайдера. TLS-проверку не отключать. Локально реальные письма не отправляются.
7. Создайте бота через BotFather и получите chat ID разрешённого получателя, сохраните TELEGRAM_TOKEN и TELEGRAM_CHAT_ID в серверном .env. Не публикуйте токен и URL Bot API в логах. Исходящий доступ к api.telegram.org:443 и SMTP-серверу нужен только обработчику очереди. Имя, телефон и комментарий в Telegram не передаются.
8. Настройте A/AAAA по данным хостинга, HTTPS-сертификат и продление, редирект HTTP→HTTPS и один основной домен. Не включайте лишние access/query-логи: для API не логировать тело, URL не должны содержать ПД. На nginx перенесите заголовки из public/.htaccess, `try_files $uri $uri/ =404`, error_page 404 /404.html; запретить исполнение PHP в assets и скрытые файлы. PHP display_errors=Off, log_errors=On, ограниченные права, HTTPS. Политика CSP приведена для Apache; проверяйте её при включении Метрики.

## Cron

Подставьте реальный путь и бинарный PHP 8.2+:

```cron
* * * * * cd /home/user/banner && /usr/bin/php8.2 bin/queue.php >> /home/user/banner/storage/queue.log 2>&1
17 3 * * * cd /home/user/banner && /usr/bin/php8.2 bin/purge.php >> /home/user/banner/storage/purge.log 2>&1
```

Настройте ротацию логов и мониторинг кодов выхода/статусов jobs через защищённые инструменты хостинга, без публичного интерфейса. Не выводите в отчёты содержимое leads. Если очередь не работает, заявки сохраняются, но уведомления ждут. Ограничьте время cron на хостинге; один запуск обрабатывает до 100 заданий.

## Публикация GitHub Actions

`.github/workflows/deploy.yml` запускается вручную. GitHub Secrets: DEPLOY_HOST, DEPLOY_USER, DEPLOY_PORT, DEPLOY_KEY (отдельный SSH-ключ), DEPLOY_PATH (существующий непубличный каталог), DEPLOY_KNOWN_HOSTS (проверенный ключ сервера, получить по доверенному каналу). Создайте environment production и защиту согласованием. Workflow переносит только публичные файлы и код, не `.env`, не vendor/storage, без --delete и без миграций. Composer на сервере запускать вручную после проверки обновлений. Перед первым релизом выполнить composer install и миграции. Устаревшие публичные файлы удалять вручную по проверенному списку (например, отключённое портфолио), не удаляя пользовательские материалы. Автопубликацию после push можно добавить отдельно после настройки.

## Резервное копирование и восстановление

Ежедневно защищённым заданием хостинга создавайте согласованную SQL-копию (`mariadb-dump --single-transaction banner` с учётными данными через защищённый option-file, не аргументы командной строки), копируйте config, реальные фото, серверный .env и lockfile в шифрованное хранилище в РФ. Установите сроки удаления копий и доступ ограниченному кругу лиц. Никогда не коммитьте дампы.

Восстановление проверять на отдельной БД: остановить cron, восстановить схему и дамп, загрузить согласованную версию кода/vendor/config, проверить document root и права .env, выполнить read-only проверку количества записей. Сохранённые sent не сбрасывать. Не запускать очередь тестового восстановления с настоящими реквизитами отправки; начать с mock. После согласования переключить DB_DSN и вернуть cron. Резервная копия также содержит ПД.
